# Interactive overview audit

Audited commit: `8c36ae7815a491218d0e6e587974b34f32cb9082`.

This is the historical audit of that commit. Its five findings are resolved in
the [audit-fix verification record](verification/2026-09-06-audit-fixes.md).

At the audited commit, the implementation did not satisfy the complete interaction contract.
Five behavior gaps were reproduced against the committed binary. The existing
suite misses those cases; its passing counts should not be treated as proof
that all input and workspace transitions are covered.

The audit left the plugin, companion patches and installed desktop unchanged.
The audited plugin SHA-256 was
`7468ddffd1c39a1cbfebaaa1d6c3993bfa7458174ccfc12f99a68d10972468aa`,
matching both `build/hyprspace.so` and the installed library at that time. Hyprland was the
pinned 0.56.2 build. The source review included the exact compositor source,
session/target handling, rendering, native dispatcher and drag hooks, launch
correlation, companion patches, and the integration harness.

## Findings

### P1: A visible bottom-layer Waybar can send clicks to a hidden window

`foregroundPointer()` in [main.cpp](../src/main.cpp) recognizes bottom/background
Waybar surfaces and yields pointer events. `renderPanels()` in
[CompositorHooks.cpp](../src/CompositorHooks.cpp) draws those panels above the
overview. Native input routing still tests ordinary windows above bottom layers.
Setting a window's fade alpha to zero does not remove it from input hit testing.

Reproduction: place a floating fixture at `(30, 30)` with size `600 × 220`,
overlapping a bottom-layer Waybar fixture. Open the overview and click the
visible panel entry. The panel receives no click. The hidden application's
Wayland log records pointer enter and both button events. Move the floating
window below the panel, repeat the click, and the panel receives it normally.
The captured image confirms the panel was visible above the overview.

This can activate an application control the user cannot see. Rendering order
and pointer routing must agree for promoted panels and their popups. A fix
should route to the actual foreground surface while preserving native grabs
and button ownership, and must include this overlapping-window regression.

Evidence: `/tmp/hs-i.n0zplwnx/audit.json` and `panel-overlap.png`.

### P2: Modifier events reach applications while the overview owns input

The hooks in [CompositorHooks.cpp](../src/CompositorHooks.cpp) suppress key
events, but leave application keyboard focus in place. The `keyboardFocus()`
hook only protects a foreground layer during dispatch. Hyprland's separate
`onKeyboardMod()` path still sends modifiers to the focused application;
focus changes can also send modifiers directly on keyboard enter.

Reproduction: focus a disposable GTK window, open the overview, and send
Ctrl+Shift+Q. Status reports `keyboard_owned=true`. The application receives
eight `wl_keyboard.modifiers` messages, including depressed masks 4 and 5,
although it receives no Q key events. The existing GTK input log only records
key press/release signals, so it cannot detect this leak.

Keyboard isolation needs to cover modifier and focus-enter delivery while
keeping the compositor's own modifier state accurate. Restoration and Walker,
IME, lock, and grab handoffs need protocol-level regression coverage.

Evidence: `/tmp/hs-i.q0_k48hq/process-1.log`.

### P2: Scrolling previews have no pointer control for off-screen columns

[main.cpp](../src/main.cpp)'s `onMouseAxis()` discards horizontal input.
[Overview.cpp](../src/Overview.cpp)'s `onScroll()` changes workspace selection
only; it never scrolls the native layout. `onMouseButton()` immediately commits
and closes when a tile/window is clicked, including a partially visible window.

Reproduction: put three tiled windows on one scrolling workspace, open the
overview, and send vertical and horizontal wheel events over its preview.
Neither changes window positions or reveals the off-screen columns. With more
workspace tiles, the vertical wheel selects another workspace instead.
Existing tests exercise scrolling-layout placement, not viewport navigation.

Recommendation: wheel/trackpad input over a scrolling tile should pan that
workspace, and visible edge arrows should advance toward hidden columns while
keeping the overview open. Keep window clicks as focus-and-close. Show arrows
only where more content exists, use the configured horizontal/vertical layout
direction, and retain Tab/Shift+Tab workspace navigation. Dwindle and master
can retain their existing wheel behavior.

The native scrolling algorithm already exposes tape movement and column
navigation. Use those through the compatibility adapter, with bounds, high
resolution input, inactive-workspace, scaling, animation, and foreground-layer
tests. A first edge-window click that reveals and a second that activates is
possible, but makes click behavior depend on clipping and animation state.

Evidence: `/tmp/hs-i.nxwb92xg/audit.json`.

### P2: A transferred launch destination still depends on its old monitor

`COverviewSession::workspace()` in
[OverviewSession.cpp](../src/OverviewSession.cpp) rejects a target whose captured
monitor is disabled or gone before looking up the workspace identity. This
invalidates destinations whose workspaces have already moved to a live output.

Reproduction: capture workspace 12 on WAYLAND-2, move that workspace to
WAYLAND-1, and disable WAYLAND-2. Workspace 12 remains alive on WAYLAND-1 with
its windows, but consuming the captured token returns an empty result. The
helper consequently falls back to native placement and loses the frozen
destination. The existing transfer test leaves the original monitor connected.

Resolve an existing workspace's identity and current monitor first. Consult
the captured monitor when recreating a missing workspace. Continue rejecting
identities that resolve to a different workspace.

Evidence: `/tmp/hs-i.6l6dufik/audit.json`, `transferred-launch`.

### P2: Single-monitor overview leaves transferred windows invisible elsewhere

The session visibility ledger in
[OverviewSession.cpp](../src/OverviewSession.cpp) restores windows only when
the session finishes. There is no reconciliation for a window leaving all
currently covered outputs.

Reproduction: set `overview:all_monitors=false`, open the overview on WAYLAND-1,
and move its window to active workspace 12 on WAYLAND-2 using the native
dispatcher. The destination output has no overview. The transferred window is
mapped and accepts input, but its fade alpha remains zero and `visible=false`.
Other windows on that destination remain visible. Closing the overview restores
the transferred window.

Visibility ownership must follow the set of covered outputs. Restore a window
when it leaves that set, preserving its original fade value, and reacquire
ownership if it returns. The default all-monitor matrix does not exercise this
configuration.

Evidence: `/tmp/hs-i.6l6dufik/audit.json`, `single-monitor`.

## Verification issues

The unmodified full-suite rerun failed the repeat assertion in
[run.py](../test/integration/run.py) immediately after key release. The test
compares a file written by asynchronously spawned commands before those
commands necessarily finish. A native-versus-overview probe produced the same
counts in both cases: 9 immediately after release, 10 after 100 ms, then 10 for
the remaining 1.3 seconds. This establishes a test timing defect, not a stuck
repeat in that reproduction. A permanent test should distinguish dispatches
after release from completion of commands dispatched before release.

A second full run passed all 84 checks, including the companion UI, Firefox,
Discord, and lock/unload checks. That run used a temporary in-memory adjustment
allowing 300 ms for already-spawned commands to finish before sampling the repeat
marker. The repository's test and plugin sources were unchanged. This is a
qualified passing run, not a passing run of the unmodified harness. Its artifact
directory is `/tmp/hs-i.7vuhv30_`; the original repeat failure is recorded in
`/tmp/hs-i.v5iozigb`.

One earlier nested startup also timed out before loading the plugin: the third
output remained 1920 × 1080 while the harness awaited 960 × 600. The retry
started successfully. This is a harness/backend startup failure; it is not
evidence of a plugin regression. The diagnostic is
`/tmp/hs-i.gdqnz1wb/output-failure.json`.

Both the nested and physical layout matrices disable compositor animations.
They therefore do not establish correctness during animated viewport motion,
rapid layout transitions, or changing geometry between pointer events. The
physical suite was not repeated during this audit. The host sanitizers do not
instrument the loaded compositor plugin.
